# 四、平台接入

> 同一套规则，四种贴法。
> **区别在于：没有脚本时，闸门是「规则」；有脚本时，闸门是「退出码」。**
> 后者不会因为模型这一次心情好就放行。

---

## 一、先选平台：能力矩阵

不同平台的差别不只在「指令框在哪」，更在于**它能不能碰你的文件**。

| 能力 | Trae | Claude / WorkBuddy | GPTs | 豆包 |
|---|---|---|---|---|
| 读本地文件 | ✅ | ✅ | ❌（需上传） | ❌（需上传） |
| 执行终端命令 | ✅ | ✅ | ⚠️ 仅沙箱内 Python | ❌ |
| 能跑 `scripts/*.py` | ✅ | ✅ | ⚠️ 需手动贴代码 | ❌ |
| 能直接发 SMTP | ✅ | ✅ | ❌（网络受限） | ❌ |
| 自定义指令入口 | `.trae/rules/` | Skill / Project Instructions | Instructions 框 | 智能体角色设定 |
| 指令字数 | 较宽松 | 较宽松 | 约 8000 字符 | 较宽松 |

> 上述能力截至本文写作时。各平台更新频繁，**以官方文档为准**。

### 结论

```
要真正发邮件、跑核查脚本  →  Trae / Claude / WorkBuddy
只要一个「会按流程办事」的顾问  →  GPTs / 豆包
```

**没有执行环境的平台，也能用这套方法论**——它会把核对表逐项问你、
帮你检查邮箱来源、指出正文里的虚假陈述。只是最后那一步发送要你自己来。

这其实未必是缺点：**发送这一步本来就该由人按下去。**

## 二、GPTs

### 贴在哪

```
Create a GPT → Configure → Instructions
```

### 用哪个文件

`prompts/gpt.md`

### 注意事项

1. **字数限制约 8000 字符。** `prompts/gpt.md` 已按此压缩，
   保留全部硬规则，删掉了大部分解释性文字。
2. **不要指望它发邮件。** 沙箱网络受限，SMTP 连不出去。
   让它做「核对表 + 正文审查 + 邮件正文生成」这三件事。
3. **附件上传。** 把你的简历传上去，它才能写出贴合的正文。
4. **Knowledge 可选。** 可以把 `docs/` 整个上传到 Knowledge，
   让它在需要细节时检索。

### 推荐的对话开场

```
我有一组校招投递目标。请按你的流程来：
先让我逐家提供公司名称、岗位、工作地点、收件邮箱、邮箱来源，
你逐项检查后给我一份核对表，等我确认再往下走。
```

## 三、Trae

### 贴在哪

```
项目根目录 → .trae/rules/project_rules.md
```

或在 Trae 的 Rules 设置里新建项目规则。

### 用哪个文件

`prompts/trae.md`

### 注意事项

1. **Trae 能读文件、能跑终端**，所以可以让它直接调用 `scripts/`。
2. **但要明确告诉它「默认干跑」。** 否则它可能「为了帮你省事」直接加 `--send`。
   在规则里写死：**任何真实发送前必须先停下来问用户。**
3. **推荐把仓库直接作为 Trae 项目打开**，这样它能看到 `drafts/` 和 `state/`。

### 推荐的对话开场

```
按 .trae/rules/project_rules.md 的流程来。
先读 drafts/ 下现有的草稿，生成核对表给我看，不要发任何邮件。
```

## 四、豆包

### 贴在哪

```
智能体创建 → 角色设定 / 人设与回复逻辑
```

### 用哪个文件

`prompts/doubao.md`

### 注意事项

1. **豆包不能执行代码、不能访问本地文件。** 纯对话式。
   所以要把它定位成**顾问**，而不是**执行者**。
2. **它更擅长对话式引导。** `prompts/doubao.md` 里写了具体的问法示例，
   让它主动逐项追问，而不是一次性丢一堆要求。
3. **发邮件这一步，让它输出「可复制的邮件正文 + 收件人 + 主题」**，
   你在邮箱客户端里手动粘。这比让 AI 直接发更安全。

### 推荐的对话开场

```
我想投校招简历。请按「先核对、后投递」的流程带我走一遍，
一家一家来，每家的公司、岗位、地点、邮箱、来源都问清楚再继续。
```

## 五、Claude / WorkBuddy

### 贴在哪

- **Claude Projects** → Project Instructions
- **WorkBuddy** → 放到 `~/.workbuddy/skills/` 下作为一个 skill

### 用哪个文件

`prompts/universal.md`

作为 WorkBuddy skill 使用时，建议结构：

```
~/.workbuddy/skills/autojobapply/
├── SKILL.md              # 主规则（可用 prompts/universal.md 改写 frontmatter）
├── scripts/              # 直接软链或复制本仓库的 scripts/
├── references/           # 复制 docs/
└── assets/
```

SKILL.md 的最小 frontmatter 形态：

```yaml
---
name: autojobapply
description: 校招邮件投递全流程——邮箱核实、投递前核对表、确认闸门、送达核查。
  当用户要投递简历到企业邮箱、核实招聘邮箱是否有效、或核查已投邮件是否送达时使用。
---
```

正文直接用 `prompts/universal.md` 的内容。

### 注意事项

1. **Claude / WorkBuddy 能跑脚本**，同样要在规则里写死「真实发送前必须停下问」。
2. **凭据走环境变量**，不要让模型把授权码写进任何文件。

## 六、没有脚本时，怎么降级

这是最需要说清楚的一节。**没有 `scripts/` 的时候，四条硬规则靠什么保证？**

| 规则 | 有脚本 | 没脚本 |
|---|---|---|
| 五项校对 | `check()` 逐项校验，缺项即阻断 | 让 AI **逐项表格化列出**，缺项标红，并要求你口头确认 |
| MX 体检 | 自动执行 + 自动阻断 | 让 AI 给你 `nslookup` 命令，**你自己跑**，把结果贴回去 |
| 确认闸门 | 退出码 3 | 在指令里写死「**未收到用户明确的『投』字，不得输出可发送的邮件正文**」 |
| 送达核查 | IMAP 自动扫 | 让 AI 给你按地址检索的手工步骤 |

### 关键差别

**脚本的闸门是机制，提示词的闸门是承诺。**

提示词能做到「大概率不犯错」，做不到「一定不犯错」。所以：

> **在没有执行环境的平台上，真实发送这一步必须由人手动完成。**
> 不要让模型「帮你发」——它连自己有没有发出去都验证不了。

### 一个务实的做法

在 GPTs / 豆包里只做前三步（调研、核实、定制），
把生成好的正文、主题、收件人复制出来，回到本地用脚本发送和核查。

```
GPTs / 豆包    →  写正文、查来源、列核对表
本地 scripts/  →  发送、核查、统计
```

这样每个平台都在做它擅长的事。

## 八、四个提示词为什么不完全一样

它们共享同一套**规则**，但做了不同的**裁剪**：

| 平台 | 裁剪方式 | 为什么 |
|---|---|---|
| GPTs | 压缩到 8000 字符内，删解释、留规则 | Instructions 有字数上限 |
| Trae | 增加「如何调用本仓库 scripts/」的操作段 | Trae 能碰文件，规则要告诉它怎么用 |
| 豆包 | 改成对话式追问脚本 + 输出格式模板 | 它不能执行，只能用对话引导 |
| universal | 全量，含方法论解释 | 给能读长文的平台用 |

**规则本身必须一致。** 如果某个平台上的规则和别的不一样，
那就会出现「在 Trae 里会被拦下的操作，在豆包里被放行」的情况。

改规则时，四份一起改。
