# 一、七步流程详解

> 这套流程的目标不是「投得多」，而是**投得准、投得真、投完知道自己在哪**。

整体关系：

```
调研 ① ──→ 核实 ② ──→ 匹配 ③ ──→ 定制 ④
                                    │
                                    ▼
                            核对表 ⑤ ──[用户确认]──→ 投递 ⑥ ──→ 核查 ⑦
                                    │                              │
                                    └──────── 统计台账 ←────────────┘
```

任何一步没有输出，就不要进入下一步。**跳过第 ② 步直接投，是在赌对方域名还活着。**

---

## ① 调研：先确认岗位上真的存在

### 要找什么

| 信息 | 为什么重要 |
|---|---|
| 公司全称（含股票代码/集团关系） | 集团与子公司同名，投错主体简历会进不相关的公司 |
| 岗位类别与具体岗位名 | 「研发类」和「技术支持类」是两个完全不同的序列 |
| **需求专业的原文表述** | 决定你能不能过简历初筛。要逐字看，不要看概括 |
| 工作地点（逐个列出） | 很多岗位的工作地是一个列表，不是单一城市 |
| 学历与届别要求 | 「2026 年 7 月前取得学位」这种表述会直接把你筛掉 |
| 简历接收方式 | **邮箱投递 / 网申 / 两者都有**，决定你后面所有动作 |

### 来源优先级

```
企业官网招聘频道  >  高校就业网原始简章  >  官方就业平台（如 24365）  >  第三方转载
```

**第三方转载只能用来「发现」，不能用来「确认」。**
看到一条信息后，回到前三级里能找到原文的那个页面去核对。

### 输出

一份候选清单，每家至少包含：公司全称、岗位名、需求专业原文、工作地点列表、投递方式。

## ② 核实：邮箱可信 ≠ 能送达

这是整套流程里最容易被跳过、也最容易出事的一步。完整方法见
[`02-email-verification.md`](02-email-verification.md)，这里只给结论：

**邮箱要过三道，缺一道就不该发：**

| 道 | 检查什么 | 失败意味着 |
|---|---|---|
| 1. 来源可追溯 | 邮箱是否出现在**你能亲自打开的官方页面**上 | 你可能在往一个二手地址投简历 |
| 2. 域名 MX 可用 | 收件域名的 MX 主机能否解析出 IPv4 | 这封信**一定**会被退回 |
| 3. 地址存在（可选） | RCPT 探测返回 250 | 地址可能不存在，或服务器拒收 |

第 2 道是硬性的。**MX 指向不存在的主机时，SMTP 依然会返回成功**——
这是本项目最重要的一条经验。

### 一个必须区分的概念

| 类型 | 典型原文 | 含义 |
|---|---|---|
| **简历接收邮箱** | 「简历投递邮箱：hr@x.com」 | 发简历到这里就是投递 |
| **咨询/联系邮箱** | 「校招咨询邮箱：hr@x.com」 | 这是给你问问题的，**不是投递入口** |

遇到第二种，正文必须写明「我会通过贵司官方网申提交正式申请，此信作为补充」，
不能让对方误以为这就是正式投递。参考 `drafts/examples/E3_咨询邮箱场景.txt`。

### 输出

每个目标的 `VERIFIED` 字段写清「在哪个页面、看到哪句话」。写不出这句话，就还没核实完。

---

## ③ 匹配：找真正重合的那一条

不要从「我有哪些技能」出发去凑岗位。反过来：

**先把岗位职责逐条拆开，再看自己的经历里哪一条能对上。**

| 岗位职责原文 | 你要能回答 |
|---|---|
| 「负责设备控制模块的软件开发与现场调试」 | 你有没有把算法/程序落到真实硬件上并现场联调过？ |
| 「参与视觉检测方案设计与算法优化」 | 你有没有独立做过一套完整的检测系统？成像条件怎么定的？ |
| 「编写技术文档」 | 你有没有写过别人能照着用的文档？ |

### 判断标准

一段经历值得写进邮件，要同时满足：

1. 能对上岗位职责里的**某一条具体描述**（不是「技术要求」里的关键词）
2. 你**能说清细节**——用到的模型、遇到的坑、最后的指标
3. 结果**可验证**——专利、奖项、上线、交付

如果一段话 HR 追问一句「具体怎么做的」你就答不上来，**不如不写**。
它只会把面试引向你最薄弱的地方。

### 输出

每个目标 2–3 段「经历 ↔ 职责」的对应关系，以及一段**技能缺口说明**（如果有）。

## ④ 定制：每封单独写

模板化是最容易被识破的。HR 一天看两百封「贵司作为行业领军企业……」，一眼就能认出来。

### 三段式结构

| 段落 | 写什么 | 不写什么 |
|---|---|---|
| 第一段 | 与岗位**核心职责**最贴近的那段经历 | 与岗位无关的获奖罗列 |
| 第二段 | 能证明**工程落地能力**的经历 | 「学习能力强」「抗压能力好」 |
| 第三段 | 对**这家公司具体产品/技术路线**的认知 | 「贵司平台广阔，能提供良好发展空间」 |

第三段是区分度最高的一段。它必须体现你**真的看过这家公司在做什么**。

### 诚实披露：把「不匹配」的解释权握在自己手里

当岗位有一项硬性要求你确实不具备时：

```
需要如实说明的是：我目前的 X 积累主要来自……，而贵司岗位中基于 Y 的
Z 开发，是我希望通过实际项目尽快补强的部分。我在……已独立完成……
有信心把新的平台与工具链尽快用起来。
如果贵司的 A 岗位更贴合我现有的经验结构，我也愿意一并考虑。
```

这段话的效果与直觉相反：**它比遮掩更有效**，因为它同时证明了三件事——
你知道这个岗位真正要什么、你不打算骗人、你给出了替代方案。

### 正文长度

**控制在 1500 字以内。** HR 平均阅读时间不到一分钟，超过这个长度基本只看第一段和最后一段。

### 输出的自检清单

发出去之前逐条过：

- [ ] 公司名是不是**这一家**（不是同集团另一家、不是简称混用的另一家）
- [ ] 岗位名是不是简章上的**原文**
- [ ] 有没有引用**我无法追溯**的企业描述（「头部」「领军」「最大」）
- [ ] 有没有写「已同步完成网申」而实际没投
- [ ] 电话、邮箱、学校、专业有没有错字
- [ ] 附件文件名是否符合对方要求的命名格式

## ⑤ 核对表：把五个事实摊开给人看

```bash
python scripts/preflight.py --dns --html
```

输出五项：**公司名称 / 投递岗位 / 工作地点 / 收件邮箱 / 邮箱来源验证**。

| 核对项 | 防的是什么 |
|---|---|
| 公司名称 | 投错主体，简历进了不相关的公司 |
| 投递岗位 | 岗位序列选错，白占一次机会 |
| 工作地点 | 投完才发现要长期驻外地 |
| 收件邮箱 | 张冠李戴，把 A 公司的信发给 B 公司 |
| 邮箱来源验证 | 把多校转载的二手信息当成已核实 |

五项任一缺失 → 标为「阻断」，不允许发送。
MX 不可用 → 同样阻断。

### 为什么必须由人来确认这一步

因为有些信息**只有当事人能判断**：
「这个城市我不去」「这个岗位序列不是我想做的」「这家公司我有别的渠道」。

程序能判断「信息是否齐全」，判断不了「这件事是否值得做」。

## ⑥ 投递：闸门 + 幂等

```bash
python scripts/send_resume.py --send --approved --only D1
```

### 四道程序约束

| 约束 | 行为 |
|---|---|
| 默认干跑 | 不加 `--send` 只打印预览，不连 SMTP |
| 双重确认 | `--send` 必须配 `--approved`，否则**退出码 3** |
| 五项校验 | 缺项即拒发该目标 |
| 幂等 | 已发送的记录在日志里，重跑自动跳过；`--force` 才重发 |

### 发送前还会再做一次 MX 复核

这一步不是重复劳动。核对表可能是在几小时前生成的，中间域名完全可能变更或被停用。
**多查一次的成本是 1 秒，漏查的代价是一次静默的无效投递。**

### 关于「发送间隔」

配置里的 `sender.interval_sec` 默认 25 秒。连续快速发信容易触发邮件服务商风控，
表现为「发送成功但对方收不到」——这种失败最难排查。

## ⑦ 核查：五段式，不要只看总数

```bash
python scripts/verify_delivery.py
```

| 部分 | 检查什么 | 关键点 |
|---|---|---|
| 一 | 发送日志明细 | 发了什么、到哪、日志里的送达状态 |
| 二 | MX 体检 | 收件域名**现在**还能不能收信 |
| 三 | 退信扫描 | 收件箱 + 垃圾箱，并把退信**归因到具体地址** |
| 四 | 「已发送」逐地址检索 | **不看总数，按地址逐个查** |
| 五 | RCPT 探测（可选） | 只探地址存在，不登录、不发正文 |

### 第四部分为什么必须逐地址查

两个原因：

1. **总数会被多轮投递混在一起。** 第一轮 5 封、第二轮 6 封，看总数只能得出
   「多了 6 封」，看不出是哪 6 封。
2. **「已发送」开关只对开启之后发出的邮件生效，不补录历史。**
   开关开启前发出的邮件在文件夹里根本不存在，看总数会误判成投递失败。

正确的做法：从发送日志里取出**每一个收件地址（含抄送）**，逐个在「已发送」里检索。
命中数才是可信的分母。

### 退信归因为什么要过滤

退信邮件（DSN）正文里会混杂大量无关地址：

```
PostMaster@qq.com
mailer-daemon@localhost.localdomain
tencent_xxxxx@qq.com
```

如果不加过滤，这些都会被当成「退信地址」报出来，把真正的问题淹掉。
正确做法：**只保留发送日志里真实出现过的地址。**

### 输出

按四级验证分别陈述结论，**不要合并成一句「投递成功」**。

## 统计台账

`state/applications.json` 是统计表的唯一数据源。

```json
{
  "meta": { "as_of": "2027-09-20", "business_scope_max_chars": 15 },
  "applications": [
    {
      "company": "某某科技有限公司",
      "business": "半导体薄膜沉积设备",
      "role": "嵌入式软件工程师（2027 届）",
      "location": "深圳",
      "channel": "邮箱",
      "applied_at": "2027-09-20",
      "delivery": "✅ 未见退信",
      "status": "已发送",
      "note": "收件 hr@example.com；官网原文核实；MX 正常",
      "draft_id": "D1"
    }
  ]
}
```

### 两个字段的语义区别

| 字段 | 回答的问题 | 取值示例 |
|---|---|---|
| `delivery` | **邮件送到了吗** | `✅ 未见退信` / `⚠️ 曾退信 已重投` / `不适用` |
| `status` | **流程走到哪了** | `已发送` / `已收到回执` / `已面试` / `未被选中` |

混在一起的后果：统计表会告诉你「20 家已发送」，但其中 3 家其实收到了退信，
你会基于错误的信息判断自己的进度。

### 为什么台账要手工维护

网申、招聘平台、内推这些渠道**没有机器日志**。只有你自己知道投了什么。
手工维护一份台账，比事后从邮箱里考古要可靠得多。

### 交叉校验

`make_stats.py` 会核对「发送日志里的工作地点」与「台账里的工作地点」是否一致，
不一致直接报错（退出码 1）。

这条校验存在的理由：一旦两处口径不一致，后面所有「投了多少家、都在哪些城市」
的判断都会失准，而且你不会发现。
