# 六、送达原理与退信归因

> 「我发出去了」和「对方收到了」之间，隔着至少四台机器和一次 DNS 查询。
> 这一节讲清楚路上会发生什么，以及为什么大多数「投递成功」的结论是不可靠的。

---

## 一、一封邮件走过的路

```
你的脚本
   │  SMTP（SSL 465）
   ▼
发件服务器（如 smtp.qq.com）        ← ① 返回 250 就发生在这里
   │  DNS 查收件域名的 MX
   ▼
收件域名声明的 MX 主机               ← ② 这一步可能失败（主机不存在 / 拒收）
   │  内部路由
   ▼
收件人的邮箱服务器                    ← ③ 地址不存在会在这里被拒
   │
   ▼
收件人邮箱（可能被判垃圾邮件）
   │
   ▼
HR 打开                             ← ④ 无法从外部观测
```

### 每一段能出什么问题

| 段 | 可能失败 | 你能看到吗 |
|---|---|---|
| 你 → 发件服务器 | 认证失败、被限流、附件超限 | ✅ 立刻看到报错 |
| 发件服务器 → MX | **域名无 MX / MX 主机不存在** | ❌ 通常延迟几秒到几分钟，**以退信形式** |
| MX → 邮箱服务器 | 地址不存在、邮箱已满、被反垃圾策略拒收 | ❌ 同样是延迟退信 |
| 邮箱服务器 → 收件箱 | 被判垃圾邮件 | ❌ 基本看不到 |
| 收件箱 → HR 阅读 | 没读、漏读、归档 | ❌ 完全看不到 |

**关键认知：只有第一段是同步的。** 后面所有失败都是**异步**的，通过退信（DSN）告诉你，
而退信本身也可能被你的邮箱服务商归到垃圾箱。

---

## 二、为什么 `SMTP 返回 250` 几乎说明不了什么

`250` 的确切含义是：

> 「我的发件服务器已经接受了你交来的这封信，我会负责投递。」

它**不**表示：

- 收件域名存在
- MX 主机存在
- 收件地址存在
- 对方服务器收下了
- 对方没有判垃圾邮件
- 有人会读

### 一个真实的失败模式

```
时间线
─────────────────────────────────────────────────
T+0s    脚本发送，SMTP 返回 250，日志记为成功
T+3s    发件服务器查 DNS：example.com 的 MX = orf.example.com
T+3s    解析 orf.example.com → 查不到任何 IP
T+4s    放弃投递，生成退信
T+15s   退信落进你的收件箱：「对方域名不存在，No Mx Record Found」
─────────────────────────────────────────────────
```

在这一整套流程里，**你的脚本看到的是「成功」**。
如果不在投递后主动扫退信，这次失败永远不会被发现。

## 三、四级验证

| 级别 | 手段 | 严格结论 | 常见误读 |
|---|---|---|---|
| ① | SMTP 返回 250 | 邮件已被**发件服务器**接收 | 「投递成功」❌ |
| ② | 收件域名 MX 可用 | 对方域名**当前**能收信 | 「地址有效」❌ |
| ③ | 无退信 / RCPT 250 | 该地址**很可能存在** | 「对方已收到」❌ |
| ④ | 收到回信 | HR 已读到 | —— |

### 汇报时的措辞对照

| 实际情况 | 应该说 | 不要说 |
|---|---|---|
| 只有 ① | 邮件已发出，尚未确认送达 | 已投递成功 |
| ①②③ | 邮件大概率已送达，未收到退信 | 企业已收到 |
| ④ | 已收到某公司回信 | —— |

这不是文字洁癖。**如果你把 ① 当成「已投递」，你会停止跟进一个其实已经断掉的机会。**

## 四、退信（DSN）怎么读

### 什么样的邮件是退信

| 特征 | 说明 |
|---|---|
| 发件人是 `postmaster@` 或 `mailer-daemon@` | 系统退信的标准发件人 |
| 主题含「退信」「无法送达」「Undelivered」「Delivery Status」「Returned Mail」 | 各服务商措辞不同 |
| 正文含 `Final-Recipient` / `Action: failed` | 标准 DSN 字段 |

### 常见退信原因对照

| 退信里的字样 | 真实原因 | 处理 |
|---|---|---|
| `No Mx Record Found` / 域名不存在 | 收件域名没有可用 MX | 换地址；这个域名整体投不进去 |
| `mailbox unavailable` / 用户不存在 | 地址错，或该员工已离职 | 换地址 |
| `mailbox full` / 容量已满 | 对方邮箱满了 | **等几天重发，或换同公司其他地址** |
| `550 5.7.1 rejected` / 反垃圾策略 | 被对方反垃圾规则拦下 | 换发件方式，或走网申 |
| `message size exceeds` | 附件太大 | 压缩附件 |
| `Connection timed out` / `4.4.1` | 对方服务器临时不可达 | 稍后重试，通常会自己恢复 |

### 「邮箱已满」是一个特殊案例

它说明：**地址是对的，人也还在，只是收不了信。**

> 真实场景：某公司的招聘邮箱 `zhaopin@<域名>` 返回「容量已满，请以其他方式通知收件人
> 清理过期邮件」。同一家公司的另一个招聘邮箱 `xyzp@<域名>` 用 RCPT 探测返回
> `250 Recipient ok`，改投后成功。

**处理策略：主地址满了，不要放弃这家公司，找同公司的其他有效地址。**

## 五、退信归因为什么要过滤

退信正文里会混杂大量与你不相关的地址：

```
From: postmaster@qq.com
To: <你的邮箱>
Subject: 退信：无法送达

您发送的邮件无法送达以下收件人：
  hr@example.com                                   ← 这才是你要找的
PostMaster@qq.com                                  ← 噪声
mailer-daemon@localhost.localdomain                ← 噪声
tencent_abc123@qq.com                              ← 噪声（服务商内部地址）
```

如果不加过滤，脚本会把所有地址都报成「退信地址」，把真正的问题淹掉。

### 正确做法

**只保留发送日志里真实出现过的地址。**

```python
known = {日志里所有 TO 和 CC 地址，小写}
失败地址 = {从 DSN 提取的所有地址} & known
```

这个交集操作能同时解决两个问题：过滤噪声，以及**把退信归因到具体是哪一封**。

## 六、「已发送」文件夹的行为

### 它默认可能是关的

QQ 邮箱等服务的「SMTP 发信后保存到已发送」是一个**独立开关**。默认可能是关闭的。

关闭时：SMTP 发送成功，但「已发送」文件夹里**没有任何记录**。
这很容易被误判成「投递失败」。

### 开关不会补录历史

**这个开关只对开启之后发出的邮件生效。** 开启前发出的邮件，永远不会出现在文件夹里。

> 真实场景：开启开关后看到「已发送」里有新邮件，于是倒推「第一轮的也应该在里面」。
> 按地址逐个检索后发现，第一轮 5 个地址命中数**全部为 0**。
> 这不是投递失败，是那个开关当时还没开。

### 所以核查必须逐地址

```python
for 地址 in 日志里的所有收件地址（含抄送）:
    命中数 = IMAP SEARCH TO <地址>
    打印(地址, 命中数)
```

### 为什么不能看总数

| 做法 | 得到什么 | 问题 |
|---|---|---|
| 看总数 | 「147 → 153，多了 6 封」 | 不知道是哪 6 封；两轮的账混在一起 |
| 逐地址检索 | 「15 个地址命中 10 个，分别是……」 | 精确，可归因，能发现缺失 |

**看总数会给你一个「大概对了」的错觉。逐地址检索会告诉你具体差在哪。**

## 七、SMTP 与 IMAP 各自负责什么

| 协议 | 端口 | 在本项目里干什么 |
|---|---|---|
| **SMTP** | 465 (SSL) / 587 (STARTTLS) | 发信。`send_resume.py` 用它 |
| **IMAP** | 993 (SSL) | 读信：扫退信、检索「已发送」。`verify_delivery.py` 用它 |

两者用**同一个授权码**（不是登录密码）。

### 授权码 ≠ 密码

| 用什么 | 结果 |
|---|---|
| 邮箱登录密码 | `SMTPAuthenticationError 535`，直接失败 |
| 授权码 | 正常 |

QQ 邮箱授权码获取：设置 → 账号 → POP3/IMAP/SMTP 服务 → 开启并生成。

**授权码等同于密码的权限，只放在环境变量里，不要写进配置文件，更不要提交。**

## 八、几个常见的错误推论

| 推论 | 为什么错 |
|---|---|
| 「SMTP 返回 250，所以投递成功」 | 250 只覆盖第一段路 |
| 「没收到退信，所以对方收到了」 | 退信可能延迟、可能被归到垃圾箱、可能被反垃圾策略静默丢弃 |
| 「已发送里有这封，所以对方收到了」 | 「已发送」只是你自己这边的副本 |
| 「对方邮箱满了等于没必要再投」 | 地址是有效的，换个同公司地址即可 |
| 「多个地址都退了，这家公司放弃」 | 可能只是这几个邮箱没人维护，网申渠道可能完全正常 |
| 「发完就完事了」 | 退信是异步的，**必须过一段时间再扫一次** |

## 九、一个务实的核查节奏

```
投递当天        → 记录日志、确认「已发送」有副本
投递后 2 小时   → 扫一次退信（大部分即时退信会在这时到齐）
投递后 1–2 天   → 再扫一次（延迟退信、容量满等临时失败会在这时出现）
每周            → 汇总台账，更新状态
```

**不要只扫一次。** 退信不是同时到达的，尤其是「邮箱已满」这类临时失败，
可能要几个小时才回。

```bash
python scripts/verify_delivery.py --days 3
```
